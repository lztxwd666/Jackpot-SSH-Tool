# 系统架构

> 定义项目的整体架构。

---

# 概述

本项目采用分层架构。

业务逻辑、平台集成和用户界面完全分离。

```
                  User
                    │
                    ▼
        ┌──────────────────────┐
        │      React UI        │
        │                      │
        │  渲染                │
        │  用户交互            │
        └──────────┬───────────┘
                   │
                   │ IPC
                   ▼
        ┌──────────────────────┐
        │    Tauri 适配器      │
        │                      │
        │  IPC 转换            │
        │  窗口生命周期        │
        │  原生集成            │
        └──────────┬───────────┘
                   │
                   ▼
        ┌──────────────────────┐
        │      SSH Core        │
        │                      │
        │  会话                │
        │  SSH                 │
        │  SFTP                │
        │  数据库              │
        │  凭据                │
        │  HostKey             │
        │  配置                │
        │  事件分发器          │
        └──────────┬───────────┘
                   │
                   ▼
        ┌──────────────────────┐
        │     系统服务         │
        │                      │
        │  ssh2-rs             │
        │  SQLite              │
        │  操作系统凭据存储    │
        │  文件系统            │
        └──────────────────────┘
```

UI 从不直接与操作系统通信。

所有操作必须经由 SSH Core。

---

# 架构原则

本项目遵循四项架构原则。

---

## 原则 1

Core 不知晓 UI。

Core 绝对不能依赖于：

- React
- Tauri
- xterm.js
- HTML
- CSS

Core 必须可作为独立的 Rust 库进行编译。

---

## 原则 2

UI 不知晓业务逻辑。

UI 绝不应当：

- 执行 SSH 操作
- 直接访问 SQLite
- 读取凭据
- 解析 SSH 配置
- 管理 HostKey
- 实现连接逻辑

UI 仅显示状态。

---

## 原则 3

IPC 是唯一的通信通道。

UI 与 Core 之间的每一次交互都通过 IPC 进行。

示例：

```
用户点击

↓

IPC 请求

↓

Core

↓

CoreEvent

↓

IPC 事件

↓

UI 刷新
```

双方都不应绕过 IPC。

---

## 原则 4

Core 通过事件进行通信。

Core 持有所有运行时状态。

每当状态发生变化：

Core 发出 CoreEvent。

消费者决定如何响应。

Core 从不直接更新界面。

---

# 各层职责

---

## UI 层

负责：

- 渲染
- 主题
- 窗口布局
- 键盘快捷键
- 拖放
- 对话框
- 通知
- 用户交互

UI 不包含任何业务逻辑。

---

## 适配器层

充当 UI 与 Core 之间的桥梁。

职责：

- IPC
- 命令路由
- 事件转发
- 窗口生命周期
- 平台特定 API

此处不应存在任何业务逻辑。

---

## Core 层

Core 是项目的心脏。

职责包括：

- SSH
- SFTP
- 会话
- 配置
- 凭据
- 数据库
- HostKey
- 运行时状态
- 事件分发

Core 应可在没有任何图形界面的情况下使用。

---

## 基础设施层

提供外部能力。

示例包括：

- SSH 实现
- SQLite
- 凭据管理器
- 文件系统
- 网络
- 日志

基础设施绝不包含业务规则。

---

# 运行时流程

应用程序遵循单向数据流。

```
User

↓

UI

↓

IPC

↓

Core

↓

Infrastructure

↓

Core

↓

CoreEvent

↓

IPC

↓

UI
```

业务逻辑始终在 Core 内部执行。

---

# 数据所有权

每种类型的数据有且仅有一个所有者。

| 数据 | 所有者 |
|-------|-------|
| 会话 | Core |
| SSH 连接 | Core |
| 运行时状态 | Core |
| 传输状态 | Core |
| HostKey | Core |
| 凭据 | Core |
| SQLite | Core |
| 窗口状态 | UI |
| 主题 | UI |
| 布局 | UI |

所有权不得重叠。

---

# 依赖规则

依赖始终向下。

```
UI

↓

Adapter

↓

Core

↓

Infrastructure
```

反向依赖是被禁止的。

示例：

UI → Core

允许。

Core → UI

禁止。

Infrastructure → Core

禁止。

---

# 事件流

系统是事件驱动的。

每个重要的状态转换都应生成一个 CoreEvent。

典型生命周期：

```
Connect

↓

Connecting

↓

Authenticating

↓

Connected

↓

Shell Ready

↓

Disconnected
```

UI 仅通过消费事件来更新。

---

# 未来的可扩展性

此架构应支持额外的前端，而无需修改 Core。

示例：

- 桌面应用程序
- 命令行界面
- VSCode 扩展
- JetBrains 插件
- 自动化测试
- 未来的 SDK

所有这些都应复用同一个 Core。

---

# 设计目标

此架构针对以下方面进行优化：

- 高性能
- 低内存占用
- 长期可维护性
- 平台独立性
- 可测试性
- 可复用性
- 清晰的职责分离

架构应在功能演进的同时保持稳定。
