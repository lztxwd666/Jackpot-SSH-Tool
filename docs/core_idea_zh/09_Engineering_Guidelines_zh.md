# 工程规范

> 定义每位贡献者必须遵循的工程规则。

这些规范确保长期的可维护性、一致性和架构完整性。

每项实现都应遵循这些规则，除非有充分且已记录的理由不这样做。

---

# 理念

架构比实现更重要。

实现可以改变。

架构应保持稳定。

当实现与架构冲突时，实现必须改变。

---

# 核心原则

## 原则 1

尊重领域边界。

每个功能恰好属于一个领域。

绝不要为了回避合理设计而创建"工具领域"或"杂项模块"。

---

## 原则 2

依赖始终向下。

```
UI
    ↓
Adapter
    ↓
Service
    ↓
Domain
    ↓
Infrastructure
```

下层绝不得依赖上层。

---

## 原则 3

业务逻辑仅属于 Core。

绝不在以下位置实现业务规则：

- UI
- IPC
- Repository
- Database
- Event Dispatcher

---

## 原则 4

每个模块应具有单一职责。

如果一个模块执行不相关的工作，拆分它。

高内聚比便利性更受偏好。

---

# 领域规则

仅在满足以下条件时引入新领域：

- 它代表一个真实的业务概念。
- 它拥有独立的生命周期。
- 它持有独立的状态。
- 它拥有明确的职责。

不要仅为组织文件而创建领域。

---

# Service 规则

Service 协调业务行为。

Service 可以：

- 调用多个领域。
- 验证业务规则。
- 发出事件。

Service 不得：

- 访问 UI。
- 访问 IPC。
- 直接访问 SQLite。
- 存储全局可变状态。

---

# Repository 规则

Repository 持有持久化。

Repository 可以：

- 加载数据。
- 保存数据。
- 查询数据。

Repository 不得：

- 验证业务规则。
- 发出 UI 事件。
- 打开网络连接。
- 知晓 SSH 协议。

---

# Provider 规则

Provider 集成外部系统。

示例：

- Credential Provider
- KnownHosts Provider
- SSHConfig Provider

Provider 应暴露一个独立于平台特定细节的清晰接口。

---

# Event 规则

每个事件代表已经发生的事情。

Event 必须：

- 是不可变的。
- 是轻量级的。
- 仅包含所需信息。

Event 绝不得：

- 执行逻辑。
- 触发副作用。
- 修改运行时状态。

---

# API 规则

每个公共 API 属于一个 Service。

API 应当：

- 执行一项操作。
- 尽可能立即返回。
- 通过事件报告长时间运行的状态。

避免创建包含不相关方法的大型"manager" API。

---

# Runtime 规则

Runtime 协调执行。

Runtime 可以：

- 调度任务。
- 分发事件。
- 持有对象注册表。

Runtime 绝不得实现业务逻辑。

---

# UI 规则

UI 是状态的消费者。

UI 可以：

- 渲染。
- 过滤。
- 排序。
- 搜索。
- 动画。

UI 绝不得：

- 持有业务状态。
- 验证 SSH。
- 访问 SQLite。
- 管理凭据。

---

# IPC 规则

IPC 是一个适配器。

IPC 应当：

- 转换请求。
- 转发事件。

IPC 绝不得：

- 实现业务逻辑。
- 修改事件。
- 维护应用程序状态。

---

# 错误处理

错误应是分层的。

基础设施错误保留在基础设施内部。

业务错误暴露给 Service。

UI 接收面向用户的错误。

避免暴露实现细节。

---

# 依赖规则

避免不必要的依赖。

在引入新依赖之前，评估：

- 它是否在积极维护？
- 它是否成熟？
- 它是否被广泛使用？
- 它是否高性能？
- 标准库能否替代解决？

偏好更少的依赖。

---

# 异步规则

异步应仅在必要时使用。

避免为纯同步操作使用异步代码。

每个派生的任务都应具有：

- 明确的所有权。
- 定义好的生命周期。
- 取消策略。

应避免分离的任务，除非有充分理由。

---

# 共享状态

共享的可变状态应最小化。

偏好：

- 所有权
- 消息传递
- 不可变数据

仅在所有权不可行时才使用同步原语。

---

# 锁规则

避免嵌套锁。

偏好较短的锁持有时间。

绝不在网络操作期间持有锁。

绝不在等待异步操作期间持有锁。

> **Stage 6 迁移中**: Worker 模型（Active Object 模式）下，锁纪律章节将逐步被消息模型规则取代。Worker 单线程串行执行所有 ssh2 操作（无锁争用），外部通过 `WorkerHandle` 的 mpsc 队列投递 `WorkerCommand`；共享状态（`SessionState`）由 `Arc<RwLock<SessionState>>` 承载，worker 为单写者、外部只读。迁移完成后，旧的 `Mutex<Option<SshConnection>>` 等字段将逐任务移除。

---

# Event 命名

Event 描述已完成的操作。

推荐：

```
ConnectionEstablished

TransferStarted

HostCreated
```

避免祈使式命名：

```
Connect

Upload

CreateHost
```

---

# 标识符规则

持久化对象持有稳定的 ID。

运行时对象持有运行时 ID。

标识符绝不复用。

避免暴露内部指针。

---

# 测试

每个领域应可独立测试。

测试应避免：

- UI
- IPC
- SQLite
- Network

尽可能 mock Repository 和 Provider，而非使用真实实现。

---

# 日志

日志应有助于调试，而不成为噪音。

推荐的级别：

- TRACE — 详细的执行流程。
- DEBUG — 内部状态变化。
- INFO — 重要的生命周期事件。
- WARN — 可恢复的问题。
- ERROR — 操作失败。

避免在热路径中过度记录日志。

---

# 性能

性能是一项设计目标。

每个功能应考虑：

- CPU 使用率
- 内存使用量
- 分配次数
- 锁争用
- 启动时间

在优化之前先测量性能。

避免过早优化。

---

# 代码审查清单

合并更改之前，验证：

- 领域边界保持完整。
- 职责清晰。
- 不存在违反架构的情况。
- 测试充分。
- 公共 API 保持一致。
- 文档在必要时已更新。

---

# 文档

架构变更必须首先更新文档。

实现应遵循文档。

文档是项目的一部分，而非事后补充。

---

# 未来的兼容性

新功能应扩展现有架构。

避免引入并列的实现。

当不确定时，偏好一致性而非新颖性。

---

# 总结

本项目遵循一条基本规则：
  
```
Architecture

↓

Engineering Rules

↓

Implementation
```

代码应当演进。

架构应当持久。

每个贡献都应加固架构，而非削弱它。
