# 架构决策记录 (ADR)

> 记录项目过程中做出的重要架构决策。

架构决策记录保存了重要技术决策背后的推理过程。

其目标是解释**为何**做出某个决策，而非**如何**实现它。

---

# ADR 原则

每条 ADR 应回答四个问题：

1. 存在什么问题？
2. 做出了什么决策？
3. 为何选择此决策？
4. 哪些替代方案被否决？

ADR 是一份历史文档。

已有的 ADR 绝不应被修改。

如果决策变更，创建一个新的 ADR 来取代前一个。

---

# ADR-0001

## 标题

Core 优先架构。

## 状态

已接受

## 背景

项目需要长期的可维护性，以及跨不同前端的可复用性。

## 决策

Core 独立于 UI 进行开发。

UI 成为 Core 服务的消费者。

## 后果

收益：

- 可复用的 Core
- 更易于测试
- 支持多前端

权衡：

- 初始复杂度略高

否决的替代方案：

- UI 驱动的架构
- 前端直接调用库

# ADR-0002

## 标题

面向领域的设计。

## 状态

已接受

## 背景

随着项目增长，基于文件夹的组织方式变得难以维护。

## 决策

围绕业务领域而非 crate 结构来组织 Core。

## 后果

收益：

- 清晰的所有权
- 更好的可扩展性
- 独立测试

否决的替代方案：

- 面向工具类的模块
- 面向技术的架构

---

# ADR-0003

## 标题

事件驱动的 Core。

## 状态

已接受

## 背景

SSH 操作是异步且状态驱动的。

UI 不应轮询运行时状态。

## 决策

Core 发布不可变事件。

UI 对事件做出响应。

## 后果

收益：

- 松耦合
- 实时更新
- 更好的可扩展性

否决的替代方案：

- 回调链
- 轮询
- 直接更新 UI

---

# ADR-0004

## 标题

分离 Session 与 Connection。

## 状态

已接受

## 背景

逻辑用户会话和网络连接具有不同的生命周期。

## 决策

Session 代表工作区。

Connection 代表活跃的 SSH 传输层。

## 后果

收益：

- 重新连接变得简单。
- 运行时状态保持稳定。
- 未来的会话恢复成为可能。

否决的替代方案：

- Session 等于 Connection

---

# ADR-0005

## 标题

一个 Connection 持有多个 Channel。

## 状态

已接受

## 背景

SSH 协议天然支持在一个传输层上建立多个通道。

## 决策

Shell、SFTP 和未来的功能共享一个 SSH 连接。

## 后果

收益：

- 更低的资源使用
- 更快的启动
- 更好的协议利用率

否决的替代方案：

- 每个功能使用独立的连接

---

# ADR-0006

## 标题

SQLite 仅存储应用程序特定数据。

## 状态

已接受

## 背景

应用程序数据与 SSH 生态系统数据不同。

## 决策

# ADR-0007

## 标题

复用 OpenSSH 标准。

## 状态

已接受

## 背景

OpenSSH 已为 SSH 配置定义了可移植的格式。

## 决策

尽可能复用 OpenSSH 兼容的文件。

示例：

- config
- known_hosts
- 身份文件

## 后果

收益：

- 更好的兼容性
- 更易于迁移
- 熟悉的工作流

否决的替代方案：

- 专有配置文件

# ADR-0008

## 标题

凭据属于操作系统。

## 状态

已接受

## 背景

否决的替代方案：

- 自定义凭据数据库

# ADR-0013

用户的数据所有权。

## 决策

- 更好的可移植性
- 更高的透明度
- 长期信任

- 封闭的专有格式

# ADR-0014

## 标题

性能是一项架构目标。

## 状态

已接受

## 背景

项目面向经常管理多个 SSH 会话的开发者。

响应性是首要需求。

## 决策

性能考量从一开始就影响架构。

优化应通过良好的设计而非事后修补来实现。

## 后果

收益：

- 更低的资源使用
- 更好的可扩展性
- 可预测的行为

否决的替代方案：

- 仅在实现后优化

# ADR 模板

未来的 ADR 应遵循此模板。

```
ADR-XXXX

Title

Status

Context

Decision

Consequences

Alternatives Rejected

Supersedes (Optional)
```

---

# 总结

架构在演进。

历史不应消失。

每个重要的架构决策都应被记录。

未来的贡献者不仅应理解架构是**什么**，还应理解它**为何**成为这个样子。
